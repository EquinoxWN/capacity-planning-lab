## Measure

Command: `caplab suite -k6 .tmp/bin/k6.exe -out docs/results/runs` (`make bench`), then
`caplab run ... stress` once more into `runs/repeat/` for repeatability. The suite runs the stress
test, takes the highest step that met the SLO before the persistent misses as the sustained rate,
then runs load and the shortened soak at 60% of it (40% headroom) and a spike to twice it.

SLO for every gated window: client p95 at most 50 ms, errors at most 1%, dropped k6 iterations at
most 1%. Server numbers come from one-second samples aligned to the first request, with the first
second of each window skipped.

## Analyze

What the numbers show:

- **The service is CPU-bound.** At the breaking point the service used 88% of its two CPUs, its
  goroutines waited up to 59 ms (p99) to be scheduled, and the queue reached its limit of 64,
  while the workers were busy only half the time and memory stayed at 16% of its limit. More
  workers would not help; more CPU (or cheaper requests) would. One request costs about 1 ms of
  CPU including HTTP handling (52% of two CPUs at 1000 req/s in calibration 3).
- **Average utilization hides saturation.** At 1900 req/s the CPU average was 88% (not 100%), yet
  the queue was full in some seconds and 1.2% of requests were shed. Arrivals are bursty at
  one-second scale, so the knee comes before 100% average utilization.
- **Handler latency is not client latency.** With one CPU (the CI configuration) the handler's
  own p95 stayed low and the queue empty while k6 saw a p95 of 1,376 ms: requests waited for the
  CPU before they reached the handler (scheduler p99 1,610 ms). Only the client view and the
  scheduler latency show it.

Defects found and their root causes:

| # | Defect | Root cause | Evidence |
|---|---|---|---|
| 1 | The busy-worker integral exceeded the pool size in a test | The worker slot was released before the busy count was decremented, so a new request could start first | `TestConcurrentLoadAccountsForEveryRequest` failed: 0.125 busy-seconds in 0.061 s with 2 workers |
| 2 | First version of the analysis put the breaking point at 400 req/s when the service sustained 1400 | One noisy step (600 req/s: p99 127 ms, scheduler p99 21 ms, host CPU up to 48%) counted as the break although four higher steps passed | [calibration 1](runs/calibration/1-first-miss-rule.md) |
| 3 | k6 dropped iterations while the service was idle | k6 starts extra VUs mid-run on demand and drops iterations meanwhile: 133 dropped at 800 req/s with the service at 23% CPU; 2,867 in a full stress run | [calibration 2](runs/calibration/2-lazy-vus.md) |
| 4 | Load at 960 req/s failed on drops twice (741 and 617) | A VU pool sized for 100 ms per request ran out whenever latency passed the queue's own 100 ms max wait ("Insufficient VUs" in the k6 log) | [calibration 4](runs/calibration/4-suite-vus-100ms/load.md), [calibration 5](runs/calibration/5-repeat-vus-100ms/load.md) |
| 5 | Gated windows miss the SLO at loads the stress test passed | Host stalls: in calibration 4's load run, at 45 to 48 s the host CPU rose to 68-73%, the service's scheduler p99 to 134-403 ms and its own CPU fell to 26-39%, so other processes held the CPUs. In calibration 5 the same windows showed each request costing about 2.3 ms of CPU instead of 1.1 ms (0.78 x 2 CPUs / 680 req/s), consistent with slower cores (efficiency cores, a busy hyperthread sibling or lower clocks); the cause inside the OS was not measured. The final soak had 18 such seconds | `samples` in [calibration 4 load.json](runs/calibration/4-suite-vus-100ms/load.json), `Stalled s` columns |
| 6 | Spike: 12,925 of 26,772 requests at 3200 req/s failed in transport | The spike scenario's fresh VUs opened hundreds of new connections at once; with the service capped at two CPUs the listen backlog filled and Windows refused 12,383 connections ("actively refused"), 542 more timed out at 2 s. These never reached the 503 shedding. Same pattern in calibration 4 (6,491 refused) | [spike.k6.log](runs/spike.k6.log) |
| 7 | The spike's "overload is refused fast" check passed during defect 6 | It looked only at the service's shed latency | `TestSpikeNeedsFastAnswersOnTheClientToo` |
| 8 | A CPU-saturated service was labelled "client-limited" | The rule looked at shed rate and handler p95 only, not at CPU saturation | quick-suite stress step03 (1 CPU): CPU 91%, scheduler p99 1,610 ms |
| 9 | govulncheck found GO-2026-6617 (HTTP/2 HPACK race) in Go 1.26.8's `net/http` | Standard library bug, fixed in Go 1.26.9 | first full check |

## Improve

| Change | Measured effect |
|---|---|
| Count the worker free before releasing its slot (defect 1) | The concurrency test passed 5 times in a row (`-count=5`) |
| Breaking point = start of the persistent misses, confirmed by a higher step (ADR 0004, defect 2) | Same data as calibration 1: 1400 instead of 400 req/s; 4 of 5 later runs agree on 1600 req/s |
| Start every VU before the test (defect 3) | Stress dropped iterations 2,867 -> 0 (calibration 2 -> 3); the machine was also less busy in run 3 (host CPU 13-29% against 33-48%), so part of the change may be the quieter machine |
| Size the VU pool for 250 ms per request (defect 4) | Load drops 741 and 617 -> 115; the requests are now sent and the misses show as latency and errors instead |
| Report host stalls per window (defect 5) | Every miss now names its stall seconds; the final load, spike and soak misses come with 8, 2 and 18 stalled seconds |
| Client p99 in the spike check (defect 7) and CPU saturation in the client-limited rule (defect 8), re-applied to the stored reports with `caplab rejudge` (no new load) | The final spike now fails the fast-refusal check; the quick suite now finds its break at 800 req/s with 1 CPU instead of calling it client-limited |
| `toolchain go1.26.9` and an HTTP/1.1-only server (defect 9) | govulncheck: "No vulnerabilities found" |

Not improved in M1 and carried to the roadmap: overload in front of the handler (defect 6; a
connection limit or a proxy in front, measured in M2), and host interference (defect 5), which
needs a dedicated machine, longer steps or repeated runs. With the interference measured here,
no rate held the SLO for a full 60 to 180 s window in the final suite; the stress test's
sustained rate is the rate the service holds when it gets its two CPUs.

## Verified only in CI, or not measured

- The `-race` run of the Go tests and the whole pipeline on Linux (`/proc/stat`, `getrusage`,
  the `linux-amd64` k6 tarball) run only in CI. The quick suite was run locally once with the CI
  flags (`-procs 1 -client-procs 2`): stress found its break at 800 req/s, load and soak passed,
  spike failed on transport errors as above.
- Not measured: host run-queue length on Windows (host saturation), network and disk (loopback
  only, no disk I/O in the service), CPU frequency and which cores the OS used, profiles (M2).
- Absolute capacity on other hardware: not claimed.

## Reproduce

```bash
make setup && make k6 && make build      # npm ci, k6 v2.3.0 into .tmp/bin (checksum-verified), caplab
make bench                               # full suite into docs/results/runs, about 8 minutes
.tmp/bin/caplab run -k6 .tmp/bin/k6 -out docs/results/runs/repeat stress
.tmp/bin/caplab rejudge -out docs/results/runs   # re-apply the analysis rules to stored reports
```

No models are used in this project, so nothing had to be deleted after the runs. Every service
ran inside the `caplab` process and every k6 process was its child; after each run no `caplab`
or `k6` process was left (checked with `Get-Process caplab,k6`).
